# CryptaShare — Cryptographic Algorithms & Mathematical Formulations

This document provides detailed theoretical and algorithmic breakdowns of all cryptographic primitives implemented within CryptaShare, suitable for evaluation in Computer Science and Cryptography courses.

---

## 1. Hybrid Cryptography: Rationale & Mechanics
Asymmetric cryptography (such as RSA) relies upon modular exponentiation over large prime factorizations. It has strict data length limits:
$$\text{Max Payload Size (RSA-OAEP)} = \frac{k}{8} - 2 \cdot hLen - 2$$
Where $k$ is the modulus bit length (e.g., 2048 bits = 256 bytes) and $hLen$ is the hash function digest length (32 bytes for SHA-256). Thus, a 2048-bit RSA key can only encrypt a maximum of $256 - 64 - 2 = 190$ bytes!

To overcome this constraint while maintaining asymmetric recipient access control, CryptaShare employs **Hybrid Cryptography**:
1. High-throughput symmetric encryption (**AES-256-GCM**) encrypts arbitrary-sized files.
2. High-security asymmetric encryption (**RSA-OAEP**) encrypts only the compact 32-byte AES key.

---

## 2. Symmetric Encryption: AES-256-GCM
**Advanced Encryption Standard in Galois/Counter Mode (AES-256-GCM)** is an authenticated encryption with associated data (AEAD) scheme providing both **confidentiality** and **authenticity**.

- **Key Size:** 256 bits (32 bytes), generated via cryptographically secure pseudo-random number generator (`crypto.randomBytes(32)`).
- **IV/Nonce:** 96 bits (12 bytes), freshly generated for every encryption operation. In CryptaShare, an IV is **never reused** with the same key.
- **Authentication Tag:** 128 bits (16 bytes), generated by GHASH polynomial evaluation over ciphertext blocks.
- **Tampering Detection:** If even a single bit of the ciphertext or IV is altered, the authentication tag verification will fail, causing decryption to immediately throw an authentication failure exception without leaking partial plaintext.

---

## 3. Asymmetric Key Encapsulation: RSA-OAEP
**Optimal Asymmetric Encryption Padding (OAEP)** is defined in RFC 8017 (PKCS #1 v2.2). It prevents chosen-ciphertext attacks (IND-CCA2 secure) by transforming the plaintext message using two Feistel-like rounds with cryptographic hash functions before modular exponentiation:

$$\text{Ciphertext } c = (M \oplus \text{MGF}(\text{seed})) \parallel (\text{seed} \oplus \text{MGF}(\dots))^e \pmod N$$

- **Modulus Size:** 2048 bits (configurable to 3072 bits).
- **Public Exponent:** $e = 65537$ (0x10001).
- **OAEP Digest:** SHA-256.
- **Usage:** Recipient's public key encrypts the ephemeral 32-byte AES session key; recipient's private key decrypts it.

---

## 4. Cryptographic Hashing: SHA-256
Secure Hash Algorithm 256 produces a deterministic 256-bit (32-byte, 64-character hexadecimal) digest:
$$\text{Digest} = \text{SHA-256}(M)$$
- **Collision Resistance:** Computationally infeasible to find $M_1 \neq M_2$ such that $\text{SHA-256}(M_1) = \text{SHA-256}(M_2)$.
- **Pre-image Resistance:** Infeasible to recover $M$ from $\text{Digest}$.
- **Avalanche Effect:** A 1-bit change in input flips ~50% of the output bits.
- **Role in CryptaShare:** Computed over original file before encryption. Receiver recomputes over decrypted file. An exact string match ($\text{originalHash} === \text{decryptedHash}$) certifies byte-level integrity.

---

## 5. Digital Signatures: RSA-PSS
**Probabilistic Signature Scheme (PSS)** is the modern standard for RSA digital signatures (RFC 8017). Unlike deterministic schemes, PSS incorporates a random salt of digest length, providing provable security in the random oracle model.

- **Hash Algorithm:** SHA-256.
- **Mask Generation Function (MGF):** MGF1 with SHA-256.
- **Salt Length:** Equal to digest length (32 bytes).
- **Signing Operation:** $\text{Sig} = \text{Sign}_{SK_{\text{sender}}}(\text{SHA-256}(M))$.
- **Verification Operation:** $\text{Verify}_{PK_{\text{sender}}}(\text{Digest}, \text{Sig}) \in \{\text{true}, \text{false}\}$.
- **Role in CryptaShare:** Guarantees non-repudiation and authenticates that the package originated from the designated sender.

---

## 6. Password-Based Private Key Protection: PBKDF2 + AES-256-GCM
To satisfy the strict requirement that private keys are **never stored as plaintext**, CryptaShare wraps the RSA private key PEM using symmetric cryptography derived from the user's password:

$$\text{DerivedKey} = \text{PBKDF2}(\text{password}, \text{salt}_{16}, \text{iterations}=100000, \text{keylen}=32, \text{digest}=\text{'sha256'})$$
$$\text{EncryptedBundle} = \text{AES-256-GCM}_{\text{DerivedKey}}(\text{PrivateKeyPEM}, \text{IV}_{12})$$

The bundle persisted in the database is a JSON object containing:
- `salt`: 16-byte random hex salt
- `iv`: 12-byte random hex IV
- `authTag`: 16-byte hex authentication tag
- `encryptedData`: hex ciphertext of the private key PEM

Even if a malicious actor gains read access to the database, they cannot recover any private key without brute-forcing the user's password against 100,000 rounds of PBKDF2.

---

## 7. Password Hashing: Bcrypt
User login passwords are not stored in plaintext or basic hashes. CryptaShare hashes passwords with **bcrypt** using a cost factor of 12 (4,096 rounds of Blowfish key schedule expansion), incorporating a random per-user salt to thwart rainbow table attacks.
